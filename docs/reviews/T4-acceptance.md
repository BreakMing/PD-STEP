## 3. P1 问题（阻塞合并）

### P1-1 C 单元测试从未执行，"可一键运行"未满足

- `host_test/test_gcode_parser.exe`（447KB）**不是 Windows 程序**：文件头 `7F 45 4C 46`，e_machine=0x00F3（Xtensa）——是 ESP32-S3 交叉编译产物，本机无法运行，目标机上也没跑过
- 时间戳证明其陈旧：ELF 构建 11:25:21，**早于** test_gcode_parser.c 最终版 11:29:24——即该二进制连"最终版测试"都不是
- 本机无任何主机 C 编译器（gcc/clang/cl 均不存在）——这是 Agent 绕道 Python 的客观原因
- 实际执行的是 `test_gcode_parser_verify.py`：**C 代码的 Python 重写版**。我复跑确认 30/30 PASS——但这是"算法验证"，不是"C 代码测试"
- Python 版与 C 版**算法不一致且未披露**（见 P1-2）

### P1-2 C 实现与 C 测试在括号注释上互相矛盾

`G1 X(hello)10`（或带空格的 `G1 X (hello) 10`）：

- **C 实现**：注释跳过仅发生在**词首**（词与词之间）。词字母后期待数值的位置遇到 `(` → `parse_float` 失败 → **error:4**
- **C Unity 测试**（test_gcode_parser.c L321）：断言 **PARSER_OK、X=10**
- **Python 版**：先全局剥注释再解析（`_strip_comment`）→ **PARSER_OK、X=10**，与测试一致，所以它全绿
- 结论：**C 测试套件若真被执行，这条必然 FAIL**。矛盾因"从未运行"而未暴露
- 附带影响：C 实现下 `G1 X5 F(hi)100`（词后紧跟注释，真实上位机可能发出的形态）也会 error:4

## 5. 决策点（需需求方拍板）

**a. 括号注释的标准行为（P1-2 修复方向）**

- 选项 1（推荐）：**修 C 代码**——词字母后的数值位置也允许 `(...)` 注释（`parse_float` 前先 `skip_comment`）。理由：PLAN §4.1 "`(...)` 内联注释忽略"的平义解读、Python 版已如此、真实上位机存在"词后紧跟注释"的形态。改动量小（parse_move/parse_g92 各一处）
- 选项 2：改测试与 Python 预期为 error:4。理由：`X(hello)10` 属病态输入，严格拒绝更保守。代价：PLAN §4.1 需加"仅词间"限定，三处要同步改

**b. 空行/纯注释行应答（P3）**

- 推荐：修订 PLAN §4.1 为"空行/纯注释行回 ok"（协议封闭性：每行恰一应答，§4.2 背压窗口计算最简单；与已上板实测的 T3 行为一致）。修订后代码零改动
- 备选：改代码不回 ok——需动 T3 已实测通过的行为，不推荐
